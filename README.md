# 手机网页版德州扑克（单机 · 6 人桌）

无限注德州扑克，固定盲注 1/2，起始筹码 200（也就是 100 个大盲），
一张 6 人桌，1 个真人 + 5 个机器人。
纯前端、零依赖、可安装为 PWA，直接跑在手机浏览器里。

**在线玩：https://yingqi0906.github.io/mobile-holdem/**

## 更新线上版本

改完代码直接 `git push`，GitHub Pages 会自动重新构建，一两分钟后生效。

如果网络需要代理才能访问 GitHub，注意 **git 不会自动读取 Windows 的「系统代理」设置**，
必须显式告诉它，否则只会看到 `Recv failure: Connection was reset`：

```powershell
$env:HTTPS_PROXY = 'http://127.0.0.1:7897'   # 端口按你代理软件实际的监听端口改
git push
```

想省事就写进仓库配置（只影响这个仓库，不动全局）：

```bash
git config http.proxy http://127.0.0.1:7897
```

万一某天代理也不通，还有个完全不依赖 `github.com` 的兜底方案 —— 直接走
REST API 发布，而且会顺带把本地分支对齐到远端提交：

```bash
node tools/deploy-github.mjs <用户名>/mobile-holdem --token-file <令牌文件路径>
```

令牌用 classic token 的 `repo` 权限，用完记得撤销。

## 跑起来

```bash
npm run serve     # 启动本地静态服务器
npm test          # 跑规则引擎的单元测试
npm run sim       # 让 6 个机器人互相对打 2000 手，输出统计
```

`npm run serve` 会打印两个地址：`localhost` 给电脑，局域网 IP 给手机。
手机和电脑连同一个 WiFi，在手机浏览器打开那个 IP 即可。

> 必须用 HTTP 打开，不能双击 `index.html`。因为项目用的是原生 ES module，
> 浏览器的 `file://` 协议不允许跨文件 import。

装到主屏：iOS Safari 用「共享 → 添加到主屏幕」，Android Chrome 用「安装应用」。
装完之后是全屏无地址栏的，并且离线也能打开。

## 代码结构

```
src/core/     纯逻辑，不认识 DOM
  cards.js      牌的整数编码（0..51）与互转
  evaluator.js  牌型评估：5 张压成一个整数，7 张取最强 5 张
  engine.js     牌局状态机：applyAction(state, action) -> state
  ai.js         蒙特卡洛胜率 + 性格参数的机器人
  rng.js        crypto 随机数 / 可播种随机数 / 洗牌
src/ui/app.js 渲染、点击翻译、定时器驱动
tests/        node:test 写的规则测试
tools/sim.js  批量模拟，用来看 AI 行为是否合理
probe.mjs     用无头 Chrome 量出真实手机视口下的元素几何（见下）
```

改样式之前建议先跑一次 `node tools/probe.mjs`：它会用 CDP 把视口设成
390×844 这种真实手机尺寸（Windows 上 Chrome 的窗口宽度有 500px 下限，
直接开窗口量不到），然后把每个关键元素的坐标、有没有互相遮挡、有没有溢出
视口全部打印出来。第三个参数可以切换到 `raise`（加注面板）或 `result`
（结算面板）状态。**靠数字判断布局，比靠眼睛猜靠谱得多。**

**引擎是纯函数式的**：每个行动都克隆一份状态、返回新状态，不碰任何全局变量。
好处是联机的时候天然就是「同步动作」而不是「同步状态」，而且测试可以直接
拿状态对象断言，不必起浏览器。

引擎里还维护着一份**整局账本** `state.session`：每个人的累计买入、每手结束后的
筹码余额、最高/最低、赢过的次数。它刻意放在引擎而不是界面里 —— 以后做联机时，
服务端跑的是同一套引擎，这份账本可以直接随状态同步给每个客户端，不需要再写
第二份统计逻辑。筹码面板里的那张多人走势图，就是纯粹从这份账本画出来的。

每次行动也带上了**类型和自增序号**（`seat.lastAction.kind` / `.seq`）。界面靠
这两个字段决定播哪种颜色的特效、以及什么时候重播动画 —— 光看文字不行，连续
两次「跟注 2」看起来是没有变化的。联机时服务端广播的动作事件会带上同样的字段。

## 已经按 TDA 规则处理好的坑

这些是德州扑克实现里最容易写错的地方，都有对应的单元测试：

- **边池**：按每个人的累计投入分层，短码玩家不参与他够不到的边池。
- **无人跟注的部分自动退回**：你下注 500、对手只有 200 全下，那 300 原样还你。
- **最小加注**：加注增量不得小于上一次的加注增量，下限是一个大盲。
- **短码 all-in 不重开下注轮**：不足额的 all-in 只提高当前注额，
  已经行动过的人只能跟或弃，不能再加注。
- **单挑特殊规则**：两人时按钮位就是小盲，翻牌前先行动、翻牌后后行动。
- **平分余数**：彩池不能整除时，余下的筹码按「按钮左手第一个」的顺序分发。
- **前注型大盲**：大盲筹码不够时，其他人仍然要按完整大盲跟注。

`npm test` 里有 24 个测试，其中两个是重点：

- **随机对抗**：多张桌子轮流打到散场，累计 800 手，每手结束都校验筹码守恒 ——
  这是验证边池有没有算错最有效的手段。
- **界面冒烟**：用极简 DOM 桩把整个界面跑起来，打完 5 手牌，专门抓
  "元素取成了 null"这类接线错误。

`npm run sim` 则是看 AI 表现得像不像人。一个健康的 6 人桌大概长这样：

```
平均底池 479　亮牌结束 29.4%　看到翻牌 42.5%　平均行动 5.8 次/手
单次决策平均耗时 1.8ms
```

亮牌率太低说明桌子太紧没有 action，太高（比如 70%+）说明大家在无脑跟注。
调 `src/core/ai.js` 里的 `BOT_PRESETS` 和翻前门槛，然后重跑这个命令即可。

## 机器人怎么打

每个机器人随机分配一种性格（岩石 / 跟注站 / 紧凶 / 松凶 / 均衡），
决策流程是：

1. 用蒙特卡洛模拟跑 200～400 次，估算自己对抗当前人数对手的胜率；
2. 和底池赔率比较，再叠加紧度、激进度、诈唬频率三个参数；
3. 偶尔慢打大牌、偶尔诈唬，避免打法被一眼看穿。

这不是最优策略（最优要上 CFR 之类的求解器），但已经能打出像样的对局。
想调难度就改 `src/core/ai.js` 里的 `BOT_PRESETS`。

### 教练（可以关）

轮到玩家行动时，操作栏上方会显示建议（加注到多少 / 跟注 / 弃牌 / 过牌），
点「为什么」展开解析：估算胜率、底池赔率、跟注的期望值是多少。玩家行动之后
会立刻复盘——如果这步有问题，会标红并说明代价（"跟注的期望是 −37 筹码，
应该弃牌"）。右上角的「教练」按钮可以随时关掉。

教练和 AI **共用同一套决策逻辑**（翻前用同一份范围表，翻后用同一个胜率与
赔率模型）。两边各写一套的话，"教练说该加注、机器人却弃牌"这种矛盾会立刻
让人失去信任。

### 这套 AI 到底有多容易被针对

```bash
npm run exploit          # 让专门的剥削策略和机器人同桌，看能赢多少 bb/100
npm run profile          # 统计机器人的行为频率，和理论值对比
```

实测（六人桌，`bb/100` 是每 100 手赢几个大盲）。**改造前**：

| 0 号位策略 | bb/100 | 标准误 | t |
| --- | --- | --- | --- |
| 对照：也用普通机器人 | +41.1 | ±33.6 | +1.2 |
| 只打大牌 | **+93.2** | ±16.7 | +5.6 |
| 宽范围偷盲 + 见牌就下注 | −277.6 | ±85.7 | −3.2 |
| 几乎不弃牌 | −341.0 | ±112.2 | −3.0 |
| 疯狂加注 | −2636.4 | ±215.0 | −12.3 |

频率分析指出漏洞是**被动且黏**：翻前主动加注只有 3.3%（GTO 平均约 30%），
被过牌后主动下注只有 30%（GTO 约 60~70%），面对中等下注只弃 23.7%
（MDF 允许弃到 36.2%）。

把翻前换成范围表（`src/core/preflop.js`）之后，**改造后**：

| 0 号位策略 | bb/100 | 标准误 | t |
| --- | --- | --- | --- |
| 对照：也用普通机器人 | +11.4 | ±21.8 | +0.5 |
| 只打大牌 | **+16.3** | ±24.2 | +0.7 |
| 宽范围偷盲 + 见牌就下注 | −89.2 | ±50.2 | −1.8 |
| 几乎不弃牌 | −538.5 | ±65.8 | −8.2 |
| 疯狂加注 | −652.1 | ±114.4 | −5.7 |

**再说翻后**。翻后最大的漏洞是胜率算错了：原来算的是"对抗随机牌"，而对手
主动下注时他的牌远强于随机牌，于是自己的胜率被系统性高估，表现就是跟注过多
（面对中等下注只弃 11.7%，而 MDF 允许弃到 36.2%）。改成按对手的投入和动作
推断范围、再从这个范围里抽样算胜率之后，弃牌率变成 **34.1% —— 正好落在理论
MDF 上**，三档下注量的防守频率全部进入合理区间。

但只按"翻前牌力"收窄还不够。对手在 Q72 面上主动下注，他的范围应该偏向
**在这个牌面上真的成牌了**的手牌，而不只是"翻前较强的牌"。所以再加一层
**逐街范围收窄**：按牌面给每个手牌类别算强度百分位（Q72 面上 72o 是两对，
强度 97%；T9s 是空气，28%），对手每做一个动作就把权重乘以"这会不会做这个
动作"的似然 —— 加注偏向强牌、过牌偏向弱牌，乘完重新归一化。

### 四步演进的效果

同样一个"只玩大牌、其余全弃"的傻瓜策略，在不同阶段能赢多少：

| 阶段 | bb/100 | 标准误 | t |
| --- | --- | --- | --- |
| 最初（启发式翻前 + 随机牌胜率） | **+93.2** | ±16.7 | +5.6 |
| 换成 GTO 翻前范围表 | +16.3 | ±24.2 | +0.7 |
| 再加上「对抗范围」的胜率 | −24.7 | ±19.6 | −1.3 |
| 再加上**逐街范围收窄** | **−1.8** | ±14.8 | −0.1 |

从"稳定赚 93 个大盲"变成**优势完全归零**。对照组也从 +41 收敛到 −2。
另外三种剥削策略同样全部为负（偷盲 −70、跟注站 −736、疯狂加注 −94）。

### 河牌 CFR 求解器

河牌是唯一能在运行时真求解的一条街（翻牌和转牌后面还有街，博弈树大到
必须抽象）。`src/core/river-solver.js` 是标准的 CFR+：

- **从英雄当前的决策点建子树**，而不是从这条街的开头建 —— 这样根节点就是
  该行动的地方，取策略不会取错节点
- **按节点预分配效用矩阵**：第一版每次迭代、每个节点都重新分配矩阵，实测
  单次要 2 秒；复用完降到 **约 100 毫秒**
- 下注尺度离散成「3/4 底池 / 全下」两档，手牌按 169 类聚合、每边保留权重
  最高的 20 类
- 胜负矩阵枚举具体组合并排除撞车 —— 这就是挡牌效应的来源

验证：Q72-9-3 牌面上，QQ（顶三条）与 AA（超对）主动下注 85%，AKo（A 高）
过牌 99%，而 AKo 的"全下"与"过牌"期望几乎相等 —— **解出了正确的无差异点**，
这正是纳什均衡该有的样子。

**只解河牌，而且只解单挑。** 这两个边界都是实测出来的，不是偷懒：

- 英雄自己的范围是"按胜率取前 X%"近似出来的，原来不包含他手里实际那两张牌，
  于是 35% 的求解直接失败。现在会把实际手牌补进范围 —— 单挑河牌点**全部能解**。
- 多人底池的河牌：150 手里**一个都没出现**。翻前改紧之后河牌几乎永远是单挑，
  所以没有为它做多人的抽象。
- 翻牌和转牌试过：把终局估值换成"打到河牌的胜率"就能复用同一个求解器，
  但结果明显是错的（AKo 在 Q72 上全下 95%）。根因是翻牌子树只走一轮下注，
  对手范围收窄不足，求解器就收敛到"反正对手会弃牌，什么都全下"。
  这是模型缺陷不是调参问题，所以这两条街**明确拒绝求解**，
  回落到范围感知的启发式。

接入之后，跟注站策略的亏损从每百手 736 个大盲扩大到 **1444 个** ——
求解器会正确地价值下注榨干它。而那个"只玩大牌"的傻瓜策略仍然是 0。
